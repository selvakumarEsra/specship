# Application flow diagram in docs/ stays current with the code graph

SpecShip already answers "how does X reach Y" through the call graph, but
that knowledge lives only in query responses. Projects keep a hand-drawn
Mermaid flow diagram under `docs/` that silently rots as flows are added,
changed, or removed — the same self-refuting drift `DOCS-DRIFT-DOC` bans
for SpecShip's own reference docs. This document specifies a generated
Mermaid flow diagram of the indexed application, written to the project's
`docs/` folder and refreshed by the indexing lifecycle whenever the flow
set changes.

<!-- id: REQ-FLOWDIAG-001 -->
## SpecShip MUST generate a Mermaid flow diagram of the indexed application into docs/

A `specship diagram` CLI subcommand renders the indexed project's
execution flows as a Mermaid `flowchart` and writes it to
`docs/flow-diagram.md` (project-root-relative) inside a fenced
` ```mermaid ` block, so it renders on GitHub and in Starlight without
tooling. The diagram is derived deterministically from the graph — entry
points (nodes of callable kinds with no incoming `calls` edge, plus
`route` nodes) and the call chains reachable from them — never from LLM
summarization. Output path MAY be overridden with `--output <path>`.
[needs user confirmation: default filename `docs/flow-diagram.md` vs
`docs/flows.md`.]

implementations:
  - src/diagram/flow-diagram.ts:collectFlows
  - src/diagram/flow-diagram.ts:renderMermaidFlowchart
  - src/diagram/flow-diagram.ts:generateFlowDiagram
  - src/index.ts:SpecShip.generateFlowDiagram

## Acceptance
<!-- id: REQ-FLOWDIAG-001.A1 -->
- Running `specship diagram` in an indexed project creates
  `docs/flow-diagram.md` containing a fenced `mermaid` `flowchart` block
  in which every edge corresponds to a `calls` edge in the graph.
<!-- id: REQ-FLOWDIAG-001.A2 -->
- Entry points (callables with no incoming `calls` edge, and routes)
  appear as diagram sources; a symbol unreachable from any entry point
  and calling nothing does not appear.
<!-- id: REQ-FLOWDIAG-001.A3 -->
- Two consecutive runs against an unchanged index produce byte-identical
  output (deterministic node ordering and IDs).
<!-- id: REQ-FLOWDIAG-001.A4 -->
- Running `specship diagram` in an uninitialized project exits non-zero
  with the standard "not initialized" guidance.

<!-- id: REQ-FLOWDIAG-002 -->
## Sync MUST refresh the diagram whenever a flow is added, changed, or removed

Once the diagram file exists, every successful `specship sync` and
`specship index` regenerates it from the fresh graph: a new call chain
appears in the diagram, a rerouted call is redrawn, and a deleted flow's
nodes and edges disappear — with no manual step. If the regenerated
content is identical to what is on disk, the file is not rewritten
(no mtime churn, no watcher loops). Auto-refresh triggers only when the
diagram file already exists or the project opts in via
`specship.config.json` (`diagram.enabled: true`); creating it the first
time is an explicit `specship diagram` run.
[needs user confirmation: opt-in default is chosen so sync never writes
into `docs/` of projects that never asked for a diagram.]

implementations:
  - src/index.ts:SpecShip.sync
  - src/index.ts:SpecShip.indexAll
  - src/diagram/flow-diagram.ts:writeFlowDiagramIfChanged

## Acceptance
<!-- id: REQ-FLOWDIAG-002.A1 -->
- With the diagram present, adding a source file that introduces a new
  call chain and running `specship sync` adds that chain to the diagram.
<!-- id: REQ-FLOWDIAG-002.A2 -->
- Deleting the file that contained a flow and running `specship sync`
  removes that flow's nodes and edges from the diagram.
<!-- id: REQ-FLOWDIAG-002.A3 -->
- Running `specship sync` with no code changes leaves the diagram file's
  bytes and mtime untouched.
<!-- id: REQ-FLOWDIAG-002.A4 -->
- In a project with no diagram file and no `diagram.enabled` config,
  `specship sync` writes nothing under `docs/`.

<!-- id: REQ-FLOWDIAG-003 -->
## The generated diagram MUST be marked generated and diff-reviewable

Consistent with `DOCS-DRIFT-DOC`: the file opens with a
"generated by SpecShip — do not edit" marker naming the regenerating
command, and content ordering is stable (sorted by module path, then
symbol name) so a flow change produces a minimal, human-reviewable git
diff rather than a wholesale rewrite.

implementations:
  - src/diagram/flow-diagram.ts:renderMermaidFlowchart

## Acceptance
<!-- id: REQ-FLOWDIAG-003.A1 -->
- The generated file's first lines identify it as generated by
  `specship diagram` and warn against hand edits.
<!-- id: REQ-FLOWDIAG-003.A2 -->
- Adding one new flow to a project changes only the lines for that flow
  (plus its subgraph header if new) in the regenerated file.

<!-- id: REQ-FLOWDIAG-004 -->
## The diagram MUST stay readable on large graphs

An application-sized graph cannot dump every callable into one chart.
Nodes are grouped into Mermaid `subgraph` blocks per top-level module
(directory), chains are truncated at a bounded depth from each entry
point, and when the node budget (default 150 nodes) is exceeded the
renderer collapses whole modules into single summary nodes labeled with
their contained-flow count rather than emitting an unreadable diagram.
Budget and depth MAY be tuned via `--max-nodes` / `--depth` flags and
matching `diagram.*` config keys.

implementations:
  - src/diagram/flow-diagram.ts:collectFlows
  - src/diagram/flow-diagram.ts:renderMermaidFlowchart

## Acceptance
<!-- id: REQ-FLOWDIAG-004.A1 -->
- A project whose flow set exceeds the node budget produces a valid
  Mermaid diagram at or under the budget with collapsed module summary
  nodes, not a truncated or invalid one.
<!-- id: REQ-FLOWDIAG-004.A2 -->
- Generated output always parses as valid Mermaid (node IDs sanitized —
  no characters Mermaid treats as syntax).
