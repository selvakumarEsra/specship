The new reality

AI assistants now write much of the code. That moved the bottleneck.

Typing is no longer slow

An assistant such as Claude Code can draft a feature in minutes.

Understanding still is

Before it can change code safely, the assistant has to work out how today's system fits together — every single session.

Rework is the new cost

Fast code that misses the intent, or quietly breaks something nearby, comes back as bugs, review rounds and re-work.

The question is no longer “how fast can we write code?” but “how fast can we ship the right code — and know it?”

SpecShip2
The product owner's problem

Your intent leaks out between the ticket and the code.

  • “Done” is a status, not a fact. A ticket says done; nothing shows which acceptance criteria are actually proven.
  • Requirements drift silently. Code changes next month and nobody notices it no longer matches what you agreed.
  • Traceability is manual. “Which code implements this requirement — and is it tested?” takes a developer's afternoon to answer.
  • AI speed amplifies all three. More code, faster, with the same blind spots.
What you actually want

For every requirement, at a glance:

  • Is it built?
  • Is it proven by a passing test?
  • Has anything changed since we agreed it?

SpecShip answers those three questions for every requirement written as a spec — and flags the moment the code moves away from them.

SpecShip3
The developer's problem

Every session, the assistant re-reads the codebase from scratch.

Ask “what happens when a user checks out?” and an assistant without a map searches files, opens them, searches again, opens more — many steps (on a large codebase, dozens) — just to find where to look.

  • Slow: time spent searching before any real work.
  • Fragile: it can miss a connection between files and break something it never saw.
  • Wasteful: the same discovery is repeated tomorrow, and by every teammate.
Analogy

A brilliant new hire with amnesia

Imagine a contractor who is excellent — but forgets the building's floor plan every morning and has to walk every corridor again before fixing a single tap.

SpecShip hands them the floor plan.

Every search the assistant repeats is time your developer waits for — and a connection it can still miss.

SpecShip6
Layer 1 · The map

A GPS for your codebase, instead of asking for directions at every corner.

  • Built automatically from the code itself — every function, every “who calls whom”, and the web routes of common frameworks. Nothing hand-maintained.
  • Exact, not guessed. The map is derived mechanically from the code's structure, never summarised by an AI — so it doesn't hallucinate.
  • Always current. It refreshes itself within seconds of a code change.
  • 20 programming languages, across web, mobile and back-end stacks.
In practice

Question: “How does a failed payment reach the customer email?”

Without the map: search → open → search → open … until the trail is found (or missed).

With the map: one lookup returns the whole path, with the relevant code, in one go.

Bonus: “what would changing this break?” is answered before anyone edits a line.

The result: the assistant spends its time on your change, not on finding its way around.

Layer 2 · The contract

A spec is a requirement you can check — not a document that gathers dust.

REQ-AUTH-001Failed logins MUST be rate-limited The login page rejects more than 5 failed attempts per minute from the same place. Acceptance A1 · The 6th failed attempt within 60 s is refused and says when to retry. A2 · A successful login resets the count. implemented by → login code proven by → rate-limit test

Simplified for the slide — real specs point at exact code and test names.

  • Plain language. Readable by a product owner; precise enough for an engineer and an AI assistant.
  • Every requirement and criterion has a permanent ID (REQ-AUTH-001, A1, A2) — so it can be tracked, linked and reported on.
  • Linked both ways: to the code that delivers it and to the test that proves it.
  • Lives with the code, so it is versioned and reviewed like everything else — and can be mirrored to JIRA.

SpecShip12
Layer 3 · The proof

Every requirement carries an honest, live status.

StatusWhat it means for you
ImplementedCode exists that claims to deliver this requirement. Not yet proven.
Verified ✓A linked test actually ran and passed. This is the only status that means “done”.
Drifted ⚠The code (or the spec) changed after it was linked. Someone should re-check it still matches.
Broken ✕Verification ran and failed. The requirement is not met today.
Orphaned ?The code it pointed to was removed or renamed. The link needs re-attaching.

“Verified” cannot be self-awarded — without real test evidence, SpecShip refuses to promote it.

SpecShip13
Layer 3 · Drift

Drift: the smoke alarm for “it used to match the requirement.”

When the code behind a requirement changes, SpecShip notices — automatically, within seconds — and flags the requirement as drifted.

  • No one has to remember which requirements a change touches.
  • Drifted items land in a review queue with one-click repair actions.
  • A requirement is only cleared when someone re-checks it — or a test re-proves it.
Example

Monday: “Refunds over $500 need manager approval” — verified ✓

Thursday: a developer refactors the refund code for performance.

Seconds later: the requirement shows Drifted ⚠ and appears in the review queue — before it reaches customers.

Drift turns “did anything change?” from a meeting into a notification.

SpecShip14
Layer 3 · Quality gates

Quality gates catch the shortcuts fast AI code is prone to.

Proof required

A requirement without a passing test isn't counted as done. Coverage reports show which criteria are proven — and which aren't.

No silencing warnings

If a change quietly switches off a quality check instead of fixing the problem, the gate spots it and stops the change.

Architecture rules

Your team's structural rules (“the UI never talks to the database directly”) are checked automatically.

Health signals

Oversized files, tangled dependencies and other warning signs surface before they become expensive.

Tests that test

Tests are written to prove each criterion, not just to pass — and, optionally, your existing test-quality tools report whether they would catch real bugs.

Only what changed

The gate can focus on just the requirements a change touches — fast enough to run on every commit.

Gates start as advisory and are switched to blocking one at a time, when the team is ready.

SpecShip24
Questions we hear

Straight answers.

Does our code go to a third party?

Not through SpecShip — its core runs entirely on your machine: no network calls, no telemetry. (Your AI assistant has its own terms.)

Will the AI change things on its own?

No. Plans, final changes, learned rules and business facts all wait for a person's approval, and the delivery workflow builds in an isolated copy. (Day-to-day edits follow your assistant's own permission settings.)

Can we trust what the map says?

It comes from the code's structure, not an AI summary — and where it can't be sure, it stays silent rather than guess.

Does it replace JIRA or our process?

No. It connects requirements to code and proof, and mirrors into the JIRA you already use. Integrations are off until switched on.

What does writing specs cost us?

A spec is a short plain-language requirement with testable criteria. The assistant drafts it from your description and asks only about gaps; you review it.

Which AI assistant — and what does it cost?

Built for Claude Code (Gemini CLI opt-in). SpecShip itself is free and open source (MIT); your assistant subscription is unchanged. Setup: two commands and a restart (plus a one-time index per project).

Do we have to write specs for everything?

No. The map works with zero specs. Add specs where proof matters most.

How soon do we see value?

The map helps from the first session after install. Specs and gates add value feature by feature, as you adopt them.
