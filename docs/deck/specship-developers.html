SpecShip for developers · 3

Install is wiring-only: it never installs the binary. It writes the MCP server to ~/.claude.json or ./.mcp.json, the slash commands, the spec-author skill and spec-driven steering. JIRA and Designer talk to external services, so they are strictly opt-in. Run the tests and the CLI on Node 24; Node 22 built-in SQLite lacks FTS5.

A deterministic code graph, not a summary

Files

Extract

Resolve

Store

SQLite + FTS5

Local. Lives in .specship/; no network, no telemetry.

Fresh. File watcher + git hooks; the index trails edits by about a second.

Honest. Unsure edges stay silent rather than guess.

SpecShip for developers · 4

Nodes are symbols such as functions, classes, routes and components; edges are calls, imports, extends, implements, references and more. Resolution adds framework patterns and dynamic-dispatch hops like callbacks and React re-renders. Everything comes from the AST, nothing is LLM-summarized.

SpecShip for developers · 5

specship_explore is primary: it returns verbatim source of the relevant symbols grouped by file, including dynamic-dispatch hops grep can’t follow. ## Acceptance

<!-- id: REQ-AUTH-001.A1 -->

- 6th failed attempt in 60 s is refused

<!-- id: REQ-AUTH-001.A2 -->

Stable IDs for every requirement and criterion

RFC 2119 keywords: MUST, SHOULD, MAY

path:Symbol links become real graph edges

In the repo, reviewed in PRs like code

SpecShip for developers · 8

Links must name a symbol, qualified for methods (Class.method). A bare file path creates no edge. Links asserted at runtime with specship_link_assert can drop on a full reindex, so durable links belong in the implementations block or in an @implements comment on the symbol itself.

SpecShip for developers · 9

All of these are /specship:spec sub-verbs except lint, which is a CLI command and runs in CI. Lint flags missing IDs, criteria with no parent, requirements with zero acceptance criteria and review markers left in acceptance bullets. Domain facts are captured with /specship:spec domain and returned inline whenever a spec or term is looked up.

STATION 06 · LINK STATE

Every link carries an honest state

StateMeans
ImplementedCode claims the requirement. Not proven yet.
Verified ✓A linked test ran and passed. The only “done”.
DriftedCode or spec changed after linking. Re-check it.
BrokenVerification ran and failed.
OrphanedThe linked symbol was renamed or deleted.

Drift is automatic: the file watcher re-checks linked code on every edit, so a refactor flips the state in seconds.

SpecShip for developers · 11

Drifted items land in the drift queue: /specship:check drifted to review it, fix or relink to repair a single spec. A requirement only clears when someone re-checks it or a test re-proves it.

PROOF

“Verified” needs test evidence

1 · Link

implementations: block, or @implements on the symbol

2 · Test

Write tests per criterion: spec behaviour

3 · Ingest

specship verify reads the vitest report, promotes or demotes

$ specship coverage REQ-AUTH-001

# per criterion: test-link state + verdict

No passing test, no Verified — an agent can’t self-award it.

SpecShip for developers · 12

Method links must be qualified (Class.method); a bare method name stays orphaned. specship_link_assert works in-session, but those links can drop on a full reindex, so make durable links in the spec or on the symbol. /specship:spec behaviour authors end-to-end tests for a requirement’s criteria.

QUALITY GATES · CI

The same checks on every commit

CommandWhat it does
specship checkFails on drift, fitness, health or behaviour
specship lintFails on malformed specs or missing criteria
specship fitnessFails on an architecture-rule violation
specship suppressionsFails when the diff adds @ts-ignore, noqa and friends
specship affectedLists only the tests your diff touches

Start advisory; switch gates to blocking one at a time.

SpecShip for developers · 13

specship check is the umbrella gate and exits non-zero on a gating failure. Locally the same thing is /specship:check with no argument. specship affected is not a gate itself; it narrows the test run to what the diff touches so the gate stays fast enough for every commit. Health detail: specship maintainability for coupling, oversized symbols, god-files, cycles and dead code.

WORKED EXAMPLE · 2/5 · SPEC

The spec it writes — three testable criteria

specs/auth-rate-limit.md

<!-- id: REQ-AUTH-001 -->

## Failed logins MUST be rate-limited per IP

## Acceptance

- A1 6th failure in 60 s → 429 + Retry-After

- A2 A successful login resets the count

- A3 Other IPs are unaffected

(each criterion carries its own id comment)

$ specship lint specs/

✓ no errors

Review it like code. It’s a markdown file in the PR.

No code linked yet — the spec exists before the implementation.

SpecShip for developers · 17

Every criterion is observable and testable, including a negative case (A3). The file passes specship lint, which is what CI runs. Optionally run /specship:spec review REQ-AUTH-001 for the quality pass before implementing.

WORKED EXAMPLE · 3/5 · IMPLEMENT

Approve the plan, get linked code

> /specship:spec implement REQ-AUTH-001

Plan · you approve

  1. RateLimiter keyed by IP
  2. Call it from LoginService.attempt
  3. Reset on success
  4. One test per criterion

src/auth/rate-limiter.ts

/** @implements REQ-AUTH-001 */

export class RateLimiter {

  check(ip: string): Verdict {

    if (this.fails(ip) >= 5)

      return blocked(this.resetIn(ip));

    return ALLOW;

  }

}

The @implements comment makes the link: REQ-AUTH-001 is now Implemented.

SpecShip for developers · 18 · code abridged

The workflow reads the spec and the map, proposes a plan and stops for approval. Reject with notes and it revises. After approval it builds in an isolated worktree and runs the gates before you see the diff. The link can be an @implements comment on the symbol, as here, or an implementations: path:Symbol block in the spec. Implemented is not done: nothing proves it yet.

WORKED EXAMPLE · 4/5 · PROVE

One test per criterion, then Verified

tests/auth/rate-limit.test.ts

/** @verifies REQ-AUTH-001.A1 */

function blocksSixthFailure() {

  fail(5, ip);

  const res = login(BAD, ip);

  expect(res.status).toBe(429);

  expect(res.retryAfter).toBeDefined();

}

it('blocks 6th failure', blocksSixthFailure);

// …same for A2, A3

SpecShip for developers · 19 · output abridged

@verifies must sit on a named function in a recognised test file; that is why the test body is a hoisted function handed to it(). A test title that names the criterion ID also links automatically. /specship:spec behaviour REQ-AUTH-001 can author these tests from the criteria. specship verify ingests the vitest JSON report and promotes or demotes each test link; without a passing run nothing becomes Verified.

SpecShip for developers · 20 · output abridged

Nobody had to remember that the rate limiter belongs to REQ-AUTH-001. The file watcher sees the linked symbol change and flips the link to Drifted within seconds. Re-running the tests shows A1 now fails, so the requirement is Broken. Fixing the comparison and re-running verify returns it to Verified, and the history shows why. In CI, specship check, or specship drifted --fail-on drifted,broken, blocks the merge.
